# Аудит, проверка и границы готовности

Исходная точка: `b56c80109eb73149c51b192cfa27c9e4f96229c6`. Изменения находятся в отдельной ветке `feature/dual-axis-ssi-bench`, проект `bench_v2`. Старый проект не считается автоматически исправленным: v2 заменяет его при отдельной прошивке, а исходные файлы оставлены для сравнения и отката.

Дополнительный дефект, пойманный при разработке v2: `RAMPMODE=HOLD` сохраняет текущую скорость и сам по себе не останавливает движение. Отключение сначала поднимает EN, затем задаёт нулевую скорость в velocity mode. Повторное включение запрещено, пока VACTUAL не равен0; старая цель нейтрализуется до подачи тока. Это проверяется моделью SPI.

## Выполненные программные проверки

- `tests/run.sh`: нативное ядро C++17 с `-Wall -Wextra -Werror -pedantic`, ASan и UBSan. Пройдены **100989 assertions**, из них100000 — перебор преобразования Gray; это не100989 различных аппаратных сценариев.
- Конечные сценарии: включение при движении, пределы, неизвестный ноль, отмена теста, потеря heartbeat, авария, независимость двух осей, StallGuard-поиск, два упора, отсутствие/залипание датчика, отказ I2C, ошибка SSI/следования, переход millis через0.
- `hardware_test.cpp`: модель SPI/GPIO проверяет регистры, отдельное замедление, запрет повторного включения при ненулевой скорости, полярность аппаратных пределов, signed24, отказ I2C, нулевую позицию SSI, линии stuck HIGH/LOW и неподтверждённый профиль.
- `ui_smoke.py`: реальный Chromium с подменённым транспортом API, без сети/железа. Проверены два размера экрана, выбор осей, редактирование параметров, угловая команда, автотест, Stop/EStop, отсутствие JS-ошибок и горизонтального переполнения.
- GitHub Actions выполняет сборку ESP32 и LittleFS, нативные тесты, сохраняет экспериментальные бинарные артефакты. Успешная сборка после исправления перегрузки Wire: run36092554029 для333ec3d. Актуальный статус последующих коммитов смотреть в Actions, а не предполагать по этой строке.

## Что НЕ проверено и НЕ заявляется

Не выполнены аппаратная прошивка владельца, осциллограммы SPI/SSI, измерение фазного тока, тепловые испытания, проверка нагрузки/торможения/ЭМС и статистика повторяемости. Модели SPI не моделируют физику двигателя, фронты, падение питания или электромагнитные помехи. Браузерный тест не исполняет серверный JSON-парсер на ESP32. Формат и питание конкретного0541211 не подтверждены. Связь с AC36 — подготовленный настраиваемый интерфейс, не сертификат plug-and-play.

Ограничения: нет гарантированной синхронизации осей, непрерывной многовитковой координаты, автокоррекции пропусков шагов, CRC SSI и разбора опционального alarm-бита, температурного/напряженческого мониторинга. Отсутствующий третий датчик допускается маской. При обрыве провода обычного активного LOW Hall отсутствие сигнала неотличимо от свободного положения. Если оси механически связаны, независимое отключение одной по ошибке может быть нежелательным: требуется отдельный общий interlock; до этого не применять их как связанную кинематическую пару.

## Приёмка на стенде — выполнять по порядку

Все пункты ниже **ожидают проверки владельцем**, а не отмечены выполненными.

1. Обесточить стенд; проверить VIO3,3В, силовой ввод, полярность, отсутствие КЗ, DIP/SD_MODE, EN/CS-подтяжки, двигатель/обмотки. Мотор1 сначала один, мотор2 отключён.
2. Проверить аварийную цепь без движения: при нажатии и разрыве мониторного провода силовая энергия снимается; после отпускания ничего не запускается. Проверить эффект при отключённой ESP32.
3. Подать24В с разумным ограничением БП. Проверить5В/3,3В и наличие SPI; нет самопроизвольного удержания/движения при загрузке, перезапуске и открытии браузера.
4. Малый паспортно допустимый ток, свободный вал: ±1°, затем известный угол; подтвердить fullSteps, microsteps, gear, направление. Ток БП не равен RMS току фазы. Нагрев контролировать независимо.
5. Движение → Stop; движение → Release; Release → быстрое повторное включение; движение → EStop; сброс ESP32 и потеря Wi-Fi. Не должно быть возобновления старой цели или автоматического продолжения.
6. Подключать Холлы по одному, проверить фактический уровень и соответствие MIN/CENTER/MAX. Проверить аппаратные REFL/REFR сначала магнитом при свободном ходе на малой скорости, включая короткий импульс. Убедиться, что от активного концевика разрешён только отход.
7. Hall-homing: свободный старт, активный датчик при старте, отсутствие магнита, неверная маска, авария во время поиска. Все незавершённые случаи сохраняют reference=false.
8. StallGuard: проверить связь SG_RESULT с нагрузкой на выбранной скорости и токе, затем ограниченные подходы к податливому/безопасному упору. Критерий repeatability задать по механической задаче и измерить; универсальный допуск не придуман.
9. SSI сначала без движения: проверить питание/полный код/полярность/кадр. Несколько известных углов в обе стороны, граница полного оборота, выключение/включение, отключение кабеля. Только потом подтвердить профиль и ноль. Не оставлять энкодер единственной защитой.
10. Второй мотор отдельно по тем же этапам; затем два независимых мотора. Проверить перекрёстное влияние токов, связь, питание и отсутствие взаимных SPI-команд.
11. Соленоид: проверить питание/диоды/ENA, одиночные импульсы, подтверждениеA/B, timeout, остывание, Stop/EStop. Нельзя ориентироваться только на нагрев корпуса L298N.
12. Один цикл ±малый угол, затем заданный рабочий диапазон внутри измеренных упоров, затем длительный тест с контролем температуры и выбросов напряжения. Результаты сохранить через диагностический JSON и отдельный протокол измерений.

Для отката прошить **оба** старых артефакта (firmware иFS) из корневого PlatformIO проекта. Перед переходом между проектами силовое питание отключить. Проводку I2C/Hall/SSI и освобождённые STEP/DIR проверить заново: старая программа выводила уровни на27/22.
